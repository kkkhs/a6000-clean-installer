# SSL 201：Windows 冻结包中的 TLS AES 初始化异常

## 已定位的故障

以下调用链对应本项目 v0.2.2 Windows 发行包的已确认打包兼容性问题：

```text
LocalMarketServer.finish_request
  → tlslite.handshakeServer
  → calcPendingStates
  → cipherfactory.createAES
  → python_aes.Python_AES
  → deprecations._func
TypeError: 'NoneType' object is not iterable
```

本地服务先发生异常，相机随后报告：

```text
Communication error 201: Error completed (SSL error)
```

**201 本身只是相机的 SSL 失败结果，不代表所有 201 都有同一个原因。** 只有完整日志出现上述 AES / `deprecations.py` 调用链时，才可对应这里的已定位问题。

## 原因

安装后端仍是 Sony-PMCA-RE 的本地 TLS 服务和 USB 安装协议。改变 APK 来源不改变该通信流程：

```text
内置文件 / 下载缓存 / 手动选择 APK
  → 原安装后端
  → USB 转发的 TLS 通信
  → 本地 TLS 服务
  → SPK 格式的应用传输
```

发行包使用 `tlslite-ng==0.8.2`。该库的纯 Python AES 实现初始化 `Rijndael` 时，会经过兼容旧类名的装饰器。装饰器调用 `inspect.getframeinfo(frame).code_context`，读取调用处的 Python 源码，并直接遍历结果。

原来的 PyInstaller spec 仅保留字节码，不收集 TLS 模块的 `.py` 源码。冻结运行时无法取得源码，`code_context` 为 `None`，于是遍历失败。源码环境可成功执行，不意味着相同代码在冻结 EXE 中也成功执行。

此前的验证只检查 TLS 证书解析，以及 **Cryptodome** 的 AES 扩展。TLS 握手实际使用的是 **tlslite 的纯 Python AES**，两者不是同一条执行路径；原验证未覆盖该冻结运行时缺陷。

## 修复范围

两个构建 spec 增加：

```python
module_collection_mode={'tlslite': 'pyz+py'}
```

在保留原字节码包的同时，附带依赖需要读取的 Python 源码；TLS 依赖固定为已复现的版本。无需修改第三方装饰器或替换加密算法。

本次修复不改变：

- Sony USB 指令和相机安装协议；
- TLS 服务的原证书、信任策略或默认握手设置；
- `127.0.0.1` 监听范围；
- APK 内容、签名、文件大小与 SHA-256；
- 防火墙、系统证书校验或全局 TLS 设置。

## 回归验证

新增 `community/tests/test_tls.py` 和 `community/pmca/marketserver/selftest.py`：

1. 在无法读取调用处源码的条件下，复现相同 `NoneType` 异常。
2. 使用 NIST AES-CBC 已知答案向量校验 tlslite 的纯 Python AES-128 / AES-256。
3. 检查两个 spec 都保留 TLS 源码。
4. 使用真实 `LocalMarketServer`，在临时 loopback 端口完成 TLS 1.0 / TLS 1.2、加密 HTTP 请求、安装动作响应及 SPK 内容往返。
5. Windows CI 在两个最终 EXE 内执行同样的 TLS 回归检查，而不仅在源码环境检查。

测试使用合成 TLS 客户端，不连接相机，不产生公开服务地址。TLS 版本和密码设置仅限制合成测试客户端；正常安装服务保留上游设置。

最终构建结果以 Release 的 `self-test-Offline.json`、`self-test-Online.json` 和 `BUILD-VERIFICATION.json` 为准。本地握手成功可以排除这条已复现的运行时崩溃，但不能证明真实相机接受证书、USB 通信正常或应用安装成功。

## English summary

The matching SSL 201 log is caused by a frozen-runtime exception, not an established certificate rejection. In tlslite-ng 0.8.2, Python AES initialization invokes a decorator that inspects caller source. Bytecode-only PyInstaller packaging leaves that source unavailable, so `code_context` is `None` and the decorator crashes.

Both specs retain tlslite source with `pyz+py`. Regression checks cover Python AES-CBC known-answer vectors and the real loopback TLS/HTTP/SPK path inside both Windows EXEs. Camera protocols, certificates, APK bytes and security settings are unchanged. Synthetic TLS peers do not establish hardware installation success.
